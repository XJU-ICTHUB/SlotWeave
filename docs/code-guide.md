# 完整引擎代码导读

引擎的完整工作链包括批量强制安放、链式动态规划、带改动价格的局部搜索、保留旧位置的分层重建、初始化搜索，以及极小规模的独立搜索器。算法推导见 [算法说明](solution.md)，接口与构建约定见 [实现说明](provenance.md)。

## 1. 从哪里开始读

先读 [src/solution.cpp](../src/solution.cpp)。它是唯一需要编译的求解器源文件，按固定顺序包含 `src/detail/` 下的18个 `.inc` 片段。**没有 `all.inc` 聚合文件，也不应把这些片段分别编译成目标文件。**

这样的组织保留了原引擎的单翻译单元语义：匿名命名空间仍在原位置打开和关闭，配置宏在原位置生效或被清理，模板与辅助函数也保持原定义顺序。`.inc` 文件是阅读边界，不是各自拥有独立接口的库。

推荐按一条完整操作路径阅读，而不是从数百个配置常量逐行看起：

1. [公开分派](../src/detail/16_dispatch.inc)：`init / apply_add / apply_remove / grid` 怎样选择普通引擎或 `tiny_search`。
2. [普通引擎入口](../src/detail/13_base_api.inc)：初始化、数量夹取、服务索引创建与回收。
3. [操作主线](../src/detail/11_operation_pipeline.inc)：`processOperation` 怎样先完成必要修改，再决定局搜和重建的工作量。
4. [状态与代价](../src/detail/01_state_and_costs.inc)：网格、同类前后继、空位索引和本次改动如何同步。
5. 再按兴趣进入 [强制安放DP](../src/detail/06_chain_dp.inc)、[重建](../src/detail/08_rebuild_layers.inc) 或 [交换下降](../src/detail/03_swap_descent.inc)。

理解 `processOperation` 时，可先把各种预算条件当作开关，只追踪数据经过哪些阶段；第二遍再看这些开关如何限制工作量。不同阶段共享网格和改动记账，顺序变化会影响后续候选，不能视为任意可交换的插件。

## 2. 模块怎样协作

| 片段 | 职责与主要入口 |
|---|---|
| `00_configuration.inc` | 固定策略、编译器选项、内部入口别名，以及各阶段的候选和预算参数。 |
| `01_state_and_costs.inc` | 整数乘除辅助、容器封装、网格和类型索引、gap代价、写入与交换的底层操作。上层算法通过这些操作维护一致状态。 |
| `02_seed_search.inc` | `runLocalSearch` 与小邻域候选。由本次改点及邻居播种，尝试改进不均衡的同类间隔。 |
| `03_swap_descent.inc` | 更完整的交换伙伴搜索、邻域缓存和队列下降；包含操作前后的受限修复及连续大操作保护所用状态。 |
| `04_gap_relocation.inc` | 以同类间隔为单位的重定位、空位修复和大批量操作后的局部链调整。 |
| `05_vacancy_placement.inc` | 空位候选查询、新类型的安放辅助，以及 `buildInitialLayout` 的分层初始构造。 |
| `06_chain_dp.inc` | `placement_dp` 命名空间。生成受限候选窗，用chain/dense DP选择增加位置，用lattice或block方案选择删除位置。 |
| `07_placement_dispatch.inc` | 将DP结果接回网格与前后继；`placeAddedGranules`、`selectRemovedGranules` 按规模和当前状态选择适用的安放路径。 |
| `08_rebuild_layers.inc` | 分层布局的赋值、应用、稠密/稀疏层DP和keep-DP。目标是在改善间隔时尽量保留已有同类型位置。 |
| `09_rebuild_policy.inc` | `buildOverlapReconstruction` 组织重建各层；`configureWorkBudgets` 设置当前规模下的工作预算和搜索参数。 |
| `10_repair_and_polish.inc` | `totalLayoutPenalty`、`minimumPossiblePenalty`，部分重建候选、回退搜索、交换退火，以及不同修复器。`currentHorizon` 提供当前前瞻尺度。 |
| `11_operation_pipeline.inc` | `processOperation` 串联强制安放、局搜、重建接受测试与后处理；维护本次操作的预算和触发条件。 |
| `12_initial_search.inc` | `polishInitialLayout`、`annealInitialLayout` 等初始化搜索。此时没有操作内的移动惩罚，但仍有计算开销。 |
| `13_base_api.inc` | 普通引擎的初始化和增删入口，处理实际数量、预热、完整状态重置、服务槽位回收和网格访问。 |
| `14_base_macro_cleanup.inc` | 清理普通引擎配置，避免它们意外改变后面的tiny引擎。它的位置属于实现语义。 |
| `15_tiny_engine.inc` | `tiny_search` 的完整实现：极小规模的精确局部代价、候选搜索和有节点预算的分支定界。 |
| `16_dispatch.inc` | `engine_dispatch` 选择引擎，并提供官方四个公开函数。选定引擎负责当前测试的后续调用。 |
| `17_macro_cleanup.inc` | 清理最后的配置宏，避免求解器被纳入评测器同一翻译单元时污染外部代码。 |

DP中的“精确”需要结合候选集合理解：有的递推精确求解给定窗口或带宽内的模型，有的间隔代价使用近似或截断。它们并不共同构成对整环在线问题的全局最优证明。tiny分支定界同样受节点预算约束。

## 3. 三类关键状态

### 网格、类型和空位

外部服务ID可以很稀疏，因此引擎先把ID映射为紧凑的内部类型槽位。**服务ID、内部类型号和格子下标是三种不同的整数，不能混用。** 空位保留内部类型0，并参与均匀度代价。

| 名字 | 含义与需要注意的不变量 |
|---|---|
| `N` | 当前圆环长度。普通引擎和tiny引擎有各自作用域内的状态。 |
| `publicGrid[i]` | 公开网格中的服务ID；`grid()` 暴露这一表示。 |
| `slotType[i]` | 格子i对应的内部类型槽位，用于高频索引访问。 |
| `serviceId[t]` / `typeIndex` | 内部类型到服务ID，以及服务ID到内部类型的映射。 |
| `typeSize[t]` | 当前类型颗粒数；`typeSize[0]` 是空位数量。 |
| `vacancyCount` | 普通引擎入口维护的可用空位数，决定增加操作的实际数量。 |
| `typeSlotCount` | 已分配类型槽位的管理边界，不等于当前非空服务数量。被删除服务的槽位可以复用。 |
| `typeHead[t]` | 类型t的圆环链表入口；空类型使用无入口标记。 |
| `nextSame[i]` / `prevSame[i]` | 同类型的圆环后继与前驱。首尾相连，单颗粒的一周间隔为N。 |

空位还使用位图加速前驱、后继和范围查询。局搜或重建写入格子时，不能只改 `publicGrid`：内部类型、同类链、空位位图及代价缓存必须一起更新。先读底层写入函数，再改上层搜索，通常比直接操作数组安全。

### 代价与缓存

`F[t]` 是类型t的整数代价权重，`cst` 计算裸gap偏差，`wcst` 计算加权代价。`setType` 在数量或相应权重变化时刷新类型代价参数；`typePenaltyDirty` 标记哪些类型的汇总代价需要重算。

`totalLayoutPenalty` 与 `minimumPossiblePenalty` 使用同一内部单位：前者描述当前布局的损失，后者给出按各类型数量计算的理想间隔下界。两者的差用于判断重建是否值得考虑。内部定点值不是直接输出给读者的U或官方总分，关系见 [题解](solution.md)。

局搜模块的临时数组经常复用，以减少分配和重复扫描。阅读时应把这些数组的生命周期和所属阶段一起看，不能仅按变量的元素类型推断含义。

### 本次操作的稳定性记账

| 名字 | 含义 |
|---|---|
| `operationStamp` | 普通引擎当前有效修改操作的时间戳；用于区分辅助数组中属于本次的记录。 |
| `changeStamp[i]` | 格子i的原值是否已在当前操作记录。 |
| `originalValue[i]` | 格子i本次首次改变前的公开服务ID。 |
| `operationCount` | 普通引擎收到的操作计数，参与在线预算策略；不能与格子改动时间戳互换。 |

`markChange` 首次写入时保存原值，`changedNow` 和 `changedIf` 用它计算当前或拟议写入的真实改动数。一个格子写入多次只按最终值是否不同计费；恢复原值可能退还改动成本。

数组中的旧数值可以留在内存中，但过期时间戳不会被当作当前操作的原值。实现没有保存可查询的历次网格、操作日志或未来请求。`hugeRun` 等小型汇总计数只用于在连续大操作下收紧前瞻与搜索，避免反复过度修复。

## 4. 固定宏为什么仍然很多

完整引擎仍保留宏配置，主要有三类用途：

- **算法与工作量约束**：窗口宽度、带宽、候选上限、评估预算、前瞻和触发条件。`ZW_* / ZC_*` 控制放置候选窗，`MN*` 控制交换下降，`OM* / RQ_*` 控制重建和部分修复，`IQ*` 控制初始化搜索。
- **当前状态与规模的分派**：tiny搜索的适用范围，稠密层与稀疏层的处理，大小批量操作的预算。这些条件将计算资源分配给适合当前规模的算法路径。
- **实现优化**：`SP* / XLS_*` 等配置保留了原有容器、查表、内联和循环实现的选择。这些配置应结合实际使用位置阅读，前缀不代表独立算法。

配置常量共同决定候选空间和运行成本。固定配置便于复现实验；调整参数时应同时检查布局质量、工作量和边界行为。

宏的定义、默认值和清理顺序已经固定。把所有 `#define` 集中搬到一个新头文件、提前展开所有表达式，或者删除看似重复的 `#undef`，都可能改变后续条件编译。18个片段因此保留原顺序；先建立行为对照，再考虑更进一步的接口封装。

## 5. 为什么保留平台优化和初始化搜索

整数乘除使用移位加法辅助函数，热点代码包含位图、查表、缓存指针和编译器相关的内联或优化声明。这些技巧用于降低间隔代价、候选查询和状态维护的常数开销。

容器封装保留了底层存储与逻辑长度的同步规则。将它直接换成普通容器、调整分配顺序或删除预热，也需要单独验证，不能仅凭“结果应该一样”认定行为与时间都不变。

初始化搜索会执行多轮构造、局搜和确定性伪随机搜索，以获得较好的起点。随机流在初始化时重置，使相同输入的搜索过程可以复现。初始化没有本步搬动惩罚，仍然消耗实际运行时间。

## 6. 修改代码时先守住哪些边界

公开接口见 [solution.h](../include/solution.h)。先保证数量、服务索引、同类链、空位位图和真实改动数的一致，再评估质量或速度。尤其应检查初始化重置、单颗粒和空类型、整类删除、全环增删、零实际变化，以及重复调用 `grid()`。

参考实现的逐步对照，只能说明被核验输入上的行为一致；实际检查范围见 [验证记录](results.md)。调整候选顺序、平局规则、随机流消耗、前瞻或修复顺序，都属于算法行为变化，应重新做完整轨迹验证。
